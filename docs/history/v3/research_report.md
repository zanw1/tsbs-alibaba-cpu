# 时序数据库实验数据构造：公开方法与 Alibaba 数据集改进

日期：2026-09-07。对象：本项目论文实验与后续独立数据库对照。结论基于一手资料、当前仓库以及本地原始 CSV；本次未测量数据库性能。

## 直接结论

最适合当前项目的是：保留真实观测、显式区分合成字段、固定子集与查询参数，再增加能解释差异的配对对照。当前已有约 2.47 亿行原始 Alibaba 记录，无需先训练生成模型或复制数据扩充规模。

本次已在独立目录落实两项数据扩展：七指标原生视图，以及与兼容版具有完全相同机器和时间键的 TSBS 对照。原 v1 数据、主机选择及主线代码均未改变。另补充八天源数据画像、子集偏移分析与 1,200 个固定参数查询实例。

需要特别修正对“完善”的理解：数据更完整的说明和更可解释的实验设计，比补满空缺或换到更容易产生非空查询的机器更有价值。当前第一天并不代表完整八天，也不能提供七个都有值的真实指标。

## 其他研究实际如何构造数据

| 工作／数据 | 构造方法与证据 | 可借鉴之处 | 不宜照搬之处 |
|---|---|---|---|
| TSBS | 分离数据生成、导入与查询；用主机数、采样间隔、时间范围和种子控制合成负载。[官方仓库](https://github.com/timescale/tsbs) | 保留生成命令与原始参考数据；固定精确查询参数 | 合成列不能因为混入一个真实指标就统称真实数据 |
| TSM-Bench，PVLDB 2023 | 从水温、水位种子扩展序列数量与长度；提供 GAN/LSH 方法并评估数据特征。[论文](https://www.vldb.org/pvldb/vol16/p3363-khelifati.pdf)、[数据构造说明](https://github.com/eXascaleInfolab/TSM-Bench/tree/main/datasets) | 分别控制设备规模、时间长度、分布特征；核查扩展数据的性质 | GAN 增广不是保持真实分布的自动保证，本项目当前无需这类扩容 |
| IoT Benchmark | 配置中独立设置数据／查询种子，支持实际文件验证、时间戳对齐、规则频率与乱序写入。[配置源码](https://raw.githubusercontent.com/thulab/iot-benchmark/master/configuration/conf/config.properties) | 将数据形状与查询负载分别定义；检查真实写入与查询结果 | 复制、异常注入属于额外压力测试，不能混入原始真实视图 |
| SciTS 数据库基准，2022／2023 更新 | 配置传感器数、维度、时间、批量与并发；v2 增加规则和不规则写入。[官方代码](https://github.com/jalalmostafa/scits) | 规模、字段宽度、采样频率、并发应是不同实验变量 | 与同名的科学时序 LLM 数据集不同，不能混淆两个 SciTS |
| DEBS 2014 Smart Homes | 基于真实家庭用电轮廓合成；按明确的设备层级建模，规定 10／20／40 栋房屋的前缀子集，保留缺测。[官方任务](https://debs.org/grand-challenges/2014/) | 固定嵌套实体集合；公开说明真实轮廓驱动合成 | 原任务是流式查询，有前视约束，不能直接将其结果当作离线索引基准 |

这些资料支持多种合理路线，没有一个统一模板要求必须填充缺测。TSM-Bench 的增广路线适合样本少而规模需求大的情况；本项目现阶段的数据量已经足够，优先保证观测、语义和控制变量更经济。

本次没有采用上述工作的数据库速度排名。论文中的历史版本、线程和运行条件不能外推到当前环境。

CPU 均值和比例以各天非空 CPU 记录为分母；这些是本地计算结果，不是引用的论文测量。第八天高 CPU 比例明显更高，具体原因未核查，不能直接归因为真实系统故障。第一天前缀缺测较多，同样不能在没有机器状态数据时断言都是采集故障。

第一天 SF1000 的 5,223,307 行只覆盖其理论十秒网格的 60.45%；单台机器的观测行数最少 79，最多 7,630。它是一份真实稀疏数据，不能用主机数乘 8,640 代替实际行数。

选中机器与第一天全体机器 CPU 经验分布的最大 CDF 差为：SF1 约 0.192、SF10 约 0.128、SF100 约 0.0156、SF1000 约 0.0105。这里仅将其作为描述性距离，未采用把相关时序点视为独立样本的显著性检验，也没有据此声称多变量分布或八天时间特征均具有代表性。SF1／10 更适合作为正确性和启动检查规模。

另一个关键发现：第一天所选 1,000 台机器的 `mem_gps`、`mkpi` 全部为空。原生版本保留七指标 schema，但实际只有五个指标有数据。`disk_io_percent` 有 4,568 条超出正常区间的源值，导出时完整保留并计数，未截断、填零或删除。

## 本次已经落实的改进

### 1. 明确三个视图的角色

`compatible` 继续引用原 v1 的 21 列数据，用来检验原引擎代码的迁移能力。它没有被重新生成或覆盖。

`native` 使用 measurement `machine_usage`、tag `machine_id` 和七个真实指标名，绝对时间仍是固定 UTC 起点加相对秒数。原始数值 token 保留；空字段在 ILP 中省略，并在预建的完整 schema 下读为 NULL。四个 SF 的原生记录是逐字节验证的嵌套子集。

`matched_tsbs` 从原来每个 SF 的 TSBS 参考文件中，筛出与 Alibaba 兼容版相同的机器和时间键。它与兼容版只有 `usage_user` 可以不同，其他九个指标、tag 和记录顺序一致。

这允许分两步解释差异：完整 TSBS 与 matched_tsbs 的比较观察稀疏记录形状影响；matched_tsbs 与 compatible 的比较观察 CPU 数值变化的影响。所有系统在每一步仍须读取同一份数据，并使用同一组查询参数。原生版改变了 schema，不能与兼容版直接计算同任务加速比。

### 2. 固定查询并暴露空结果

每个 SF 使用当前仓库的 Q1–Q15 参数生成器，每类 20 个实例，种子固定为 10001–10020；共 1,200 条 JSONL 记录，包含 SQL、参数、输入行数和预期输出行数。种子未根据值或执行耗时挑选，空查询没有删除。Q1 没有参数，因此其 20 条实例不代表 20 个不同查询，文件内另外记录实际不同参数数量。

| SF | Alibaba 空输出实例／300 | 配对 TSBS 空输出实例／300 | Alibaba Q11 空输出实例／20 |
|---|---:|---:|---:|
| 1 | 44 | 8 | 20 |
| 10 | 37 | 18 | 19 |
| 100 | 19 | 4 | 19 |
| 1000 | 27 | 16 | 20 |

表中行数来自源数据与查询合同计算，尚不是对全部查询的数据库执行验证。特别是 Q11 在 SF1000 的这批实例全部为空，不能以这批查询的快速返回证明复杂过滤或宽行物化能力。

后续可以另设明确命名的阈值／选择率敏感性实验，但不能替换既有 CPU>90 主对照，也不能只留下非空实例。当前 Q15 仍按本项目升序 LIMIT 语义处理，未改成其他系统模板的“最后五个桶”。

### 3. 保留来源、计数与验证工具

文件清单、空值计数、异常值计数、原始来源、机器映射、查询种子及范围都保存在 JSON 中。配对数据逐行比较；原生数据检查键、CPU、空字段计数和嵌套性。另以临时 QuestDB 表核查 SF1 的全部九列和 NULL 位置。验证运行及边界见 `validation.json`；临时表配置导致的失败诊断保留于 `validation_attempts.jsonl`。

两套数据处理代码都位于本研究目录，没有往主线增加数据库 provider 或修改 generated query。旧 v1 已经验证过 loader/builder；本次新增 native schema 不能因此自动认定可由旧 C++ 引擎读取。

## 仍需由实验回答的问题

1. 第一天结果只能支持第一天场景。跨时间分布结论至少需要预先定义的多个日窗口；本次遵守已选定的一天规模，没有悄悄改为第八天或扩大八天实验。
2. 如果研究目标必须包含全部七个活跃指标，需要先确定其他日窗口的逐字段覆盖，再制定窗口选择规则；不能凭当前第一天补造两个缺失指标。
3. 兼容视图的辅助指标仍按每个 SF 独立生成，因此 CPU／机器／时间嵌套不等于全部合成指标逐字节嵌套。为了保留 v1 的既有对照，本次只让原生视图严格嵌套，没有改写旧数据。
4. 主线准备检查、稀疏桶正确性以及跨数据库计时边界仍需要另行处理。数据构造通过不是完整引擎查询正确性通过，更不是性能优势证明。

## 推荐实验顺序

先使用 compatible 与 matched_tsbs 做固定引擎、同 schema 的配对实验；用 SF100／1000 作为主要规模，SF1／10 验证边界。随后根据论文要主张的范围决定是否执行 native 真实五个活跃指标的查询，或增加预先固定的多个日窗口。需要真正不同领域时再接入 Intel Lab。

本次采用有范围的深度检索，不称为穷尽式系统综述。对于同名但研究对象不同的 SciTS、TSM-Bench，以及仅针对预测模型的 TS Benchmark，进行了区分，没有作为数据库数据构造证据混用。资料足以覆盖合成、真实、真实轮廓增广、缺测与规模设计，故停止继续扩展泛化搜索。
